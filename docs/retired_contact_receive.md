# STEP 63: preserve retired peer ratchets; explicit receive-only recovery

Implementation supplied; native target tests pending. Transfer/contact-continuity flags remain OFF. Ordinary decrypt()/message delivery does NOT call retired receive in this step. Not a completed transfer release.

Before deleting an old peer session during a native certificate-verified continuity transaction, retain its serialized ratchet plus old public identity in account-scoped platform secure storage. Bind each entry to stable peer account UUID, from/to epochs and the existing local identity hash. Maximum four snapshots / 1 MiB per peer. No eviction on overflow: refuse the transition and restore the prior state rather than silently lose a receive session. Expired snapshots are retained; no automatic secret deletion policy is introduced.

Journal version 3 snapshots the previous archive along with trusted identity/session/continuity metadata. Failure or restart restores all of them before deleting the journal. Legacy v1/v2 journals remain readable. Archive persistence/readback must complete before the live session is changed. The successful native transition still owns the only active trusted peer key/epoch.

Explicit decryptRetiredContactMessage / decryptRetiredPeerMessage accepts only ordinary Signal messages (type 2), never a pre-key handshake. Check current peer metadata against active pinned identity; match archive account/epoch/local identity; enforce a maximum seven-day receive window. Native decryption runs on an isolated in-memory session/identity adapter, which does not replace active peer identity/session. Persist the advanced archived ratchet with readback before returning plaintext. Failed authentication/replay does not commit archive changes. A changed local identity cannot use the archive. Calling service API retains existing per-peer lock/session guards; low-level store API requires caller to hold that lock. One local profile writer is still required; cross-process secure-store races are not solved.

Important security/product limit: an old valid ratchet cannot prove a message was sent BEFORE retirement. A compromised old device may authenticate new traffic during a receive grace period. Seven days is a prototype upper bound, not an approved security policy. Ordinary delivery remains disconnected until a reviewed grace policy, explicit retired-key labeling and message eligibility/UI behavior are implemented. No blind fallback to a retired key. New-phone history/local-identity transfer is NOT implemented by this peer archive; a new phone without old private state cannot decrypt old addressed ciphertext merely from public certificates. This step addresses an existing contact's local peer ratchet continuity.

Tests supplied use actual native Signal handshake/ratchet and mock secure storage: out-of-order late messages; unchanged active trust/session/epoch; replay; tampering; fresh-store restart; stale callback; pre-key rejection; v3 transaction rollback; expiry; capacity; corrupt archive retention. Previous transfer/contact/legacy journal regressions also run. Test secrets are synthetic; real account keys, contacts and history are untouched. No server source changes, server restart/deploy, website or GitHub publication.

Still pending: approved retired-key UI/receive eligibility and delivery caching under cancellation, process-wide profile writer enforcement, old/new device state/history transfer, lost-old-device behavior, directory freshness review, real two-device Android/Windows tests and release audit.
