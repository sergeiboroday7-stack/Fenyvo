# STEP 62: old-device proof ACK and correlated contact continuity routing

Implementation supplied. Target Dart/native checks pending. Transfer and contact-continuity flags remain default OFF. No deployment, production ledger or real key/peer data changes.

Old-device v2 approval waits up to 10 seconds (bounded by request expiry) for an exact one-field ACK with matching nonce, current pending request and socket/account generation. A send result alone is insufficient. The ACK means the server received the old proof, not that the new phone is active. Cancellation/replacement/timeout fails the pending ACK; an obsolete ACK cannot satisfy a later scope. V1 retains its prior send behavior. RU/UK/EN status/error text distinguishes waiting and missing acknowledgement.

When FENYVO_CONTACT_CONTINUITY_ENABLED is explicitly enabled in a future tested development build, a normal requested peer bundle first reads the pinned public identity/epoch. Same-key and first-contact behavior is unchanged. A changed pinned key requires a fresh certificate-directory request with a random 256-bit correlation id, exact echo, peer, epoch, available/current full chain (maximum 32 transitions), and matching stored account UUID if known. Partial/stale/mismatched/oversized replies stop the update. Server correlation echo is optional for legacy callers but validates supplied ids; the new client requires it. Existing authenticated accepted-contact/block policy is retained. Unsolicited directory responses are never applied.

The router cannot grant trust: the actual callback is SignalE2eeService.acceptContinuityVerifiedRemoteBundle, which rechecks the pinned old key, native Signal certificate chain, final bundle identity, metadata account/epoch and signed bundle, then uses its existing recovery journal for session/key/epoch changes. No plaintext fallback or bypass of signature verification. Directory/account identifiers alone do not establish trust. A directory can still withhold a newer head; no key-transparency/freshness guarantee is claimed. If trusted peer state changed while awaiting, native verification refuses stale chains.

Validation: ACK lifecycle tests; routing context and failure tests; existing native contact continuity/replay/rollback tests and prior transfer tests. Server actual-handler/ledger tests verify auth, contact blocking, correlation echo and malformed correlation rejection (42 tests run locally). Native tests run on the target Windows SDK. Real socket-to-peer automatic key update, pending old ciphertext policy, single profile writer enforcement, full Android/Windows transfer and history migration remain pending. Do NOT enable contact auto-routing for real accounts before old-session in-flight message handling is resolved and tested. Local server module source is updated, but the working/public server is not started or deployed; server.js unchanged.
